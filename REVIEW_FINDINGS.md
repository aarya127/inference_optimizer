# Full Codebase Review — Detailed Findings

Generated by a five-track review (controller/batching, simulation modules, integrated service, calibration/evaluation, methodology). Findings are grouped by theme, then by file, each with location and severity.

**Severity key:** 🔴 Critical (headline claim unsupported or system-breaking) · 🟠 High · 🟡 Medium · ⚪ Low

## 1. Study-validity issues (these matter more than any code bug)

### 1.1 🔴 The 5,991 ms "vision encoding" figure was never measured
- `baseline/results.json` records `t_vision_ms` ≈ **112–128 ms** across all resolution sweeps. The 5,991 ms figure comes from `model_calibration/cost_model.py:48-49`: `# = 8489ms − 2498ms = 5991ms` — it is the *residual* between the measured end-to-end prefill (8,489 ms) and the fitted LM prefill model (2,498 ms), relabeled as "vision."
- `README.md:179` calls it "Phase 1 measurement." It appears in no results file.
- The residual plausibly reflects MLX lazy evaluation folding vision compute into the "prefill" timing — `baseline/run_experiments.py:78-86` calls `mx.eval()` **with no arguments**, which is a no-op and synchronizes nothing, so the stage split is unreliable.
- Every headline number (24.4× speedup, 349 ms AMIO TTFT, all of Figs 1–5, the A100 projection) is parameterized by this constant.

### 1.2 🔴 The cost model's only true validation failed at 70.6% error — and was omitted from every report
- `model_calibration/calibration_results.json` `"validation"` block: `t_baseline_actual: 8489.27, t_baseline_pred: 2492.27, error_pct: 70.64`. Never mentioned in README or FINAL_REPORT.
- The claimed "MAPE 2.55% on held-out points" (`README.md:92`) is **in-sample**: `calibrate_cost_model.py:143-149` fits and scores on the same 7 points; `evaluation/generate_report.py:625-651` "validates" on the training set. There are no held-out points anywhere in the repo.

### 1.3 🔴 The repo's own baseline data refutes the crop-scaling premise
- `baseline/results.json`: `visual_tokens = 1548` and TTFT ≈ flat (8.5–8.8 s) at **all** of 224 / 512 / 1024 px — the processor tiled every input identically, so resolution→crop control was never actually exercised or measured. Phases 3–8 assume T_vision ∝ n_crops with the map {224→1 … 1512→24}; that linearity is asserted, not calibrated (`simulation/resolution_scaler.py:128-130`).

### 1.4 🔴 Headline results are hardcoded literals in the report generator
`evaluation/generate_report.py`:
- `:1029-1033` — the entire "System comparison" table (Static 4.7% / AMIO **55.6% / 587 ms / 0.83 / 5.3%**) is literal markdown, not computed.
- `:753-757` — abstract numbers injected via `.format(50.9, 57.5)`.
- `:744, :785, :954-955, :1054-1057, :1096, :1102-1105, :1264-1266` — quality 0.83, fragmentation 62.8→5.3 (three places), the memory-efficiency table, and the console "key results" are all literals.
- Consequence: re-running the evaluation cannot change the "results." The report is unfalsifiable by its own pipeline.

### 1.5 🔴 Simulated values labeled "measured"
- `evaluation/vllm_baseline.py:164-165`: `m3_amio_ttft_ms = 349.0` labeled "Phase 8 measured"; `:159`: `m3_naive_kv_frag = 62.8 # measured` — both are simulation outputs. Figure/table labels say "measured" and "p50" though no percentile was ever recorded.
- The "hardware-independence" finding (24.4× vs 22.3× on A100) is circular: the A100 numbers are M3 numbers divided by constants, so the ratios match algebraically (`vllm_baseline.py:204-205, 420-423`).
- The static `REPORT_SECTION` table (`:408-414`) hardcodes concurrency "≤2 / 8 / 222 / 888" which contradicts what the script's own `max_concurrent_seqs()` computes (~40 / 181 / 227 / 928).

### 1.6 🔴 No model is ever loaded or run anywhere
- `integrated_service.py` never imports `models/multimodal_loader.py` or `models/quantization.py`. The "OpenAI-compatible API" returns a fabricated string (`content = f"[AMIO] req=..."`, `integrated_service.py:671-714`) with invented `usage` token counts, under the model name `SmolVLM-Instruct-4bit-AMIO`.
- `models/multimodal_loader.py` is scaffolding: "loading" assigns config dicts (`:101`), `encode_image` returns `mx.zeros(...)` (`:173`), `generate` returns a canned f-string (`:199`) — and it targets LLaVA/Qwen, not SmolVLM.
- All worker latencies are analytic formulas + Gaussian noise; `X-AMIO-Actual-TTFT-MS` headers report formula evaluations.

### 1.7 🔴 Quality "7.5× gain" is an inverted 12× loss on a self-defined proxy
- Quality = `n_crops × keep_ratio` (`integrated_service.py:955-965`, axis label at `generate_report.py:481`) — an input-compute proxy, not accuracy. No VQA benchmark exists in the repo despite `docs/DESIGN.md:167` promising VQAv2/GQA.
- By its own metric AMIO scores **0.83 vs baseline 10.25** (8% of baseline); README's "7.5×" switches the comparator to Greedy (0.11) to show a gain. FINAL_REPORT calls this "accuracy gain."

### 1.8 🟠 The benchmark's "3-system comparison" is circular
- `integrated_service.py:_simulate_system` (:873+) grades all three systems with the same Phase-2 cost model the AMIO controller optimizes against, + 3% noise. The controller is graded by the simulator it was built to satisfy.
- Exception path injects hardcoded fragmentation (`frag = 1.5 if AMIO else 75.0`, `:1005-1008`) straight into the headline claim. "Throughput" is offered load, not achieved (`:1023, :1036` — no service time elapses).

### 1.9 🟠 Fabricated hardware model
- "38 GPU SMs" (`simulation/controller.py:64`): the 8 GB / 100 GB/s M3 is the base M3 with a **10-core GPU**; "SM" is NVIDIA nomenclature; 38 matches no Apple part. Metal/MLX exposes no per-task core partitioning (FINAL_REPORT §2.3 discloses this; README:5,127 does not).
- Single-chip tensor parallelism: `controller.py:522-524` applies a magic ×0.75 prefill speedup ("TP") on a one-GPU machine; `tp_simulator.py:134` computes gains as `t_compute/tp_size` — the speedup **is** the assumption. This fictitious 25% discount is inside the headline 349 ms.
- "FP8 7.2 TFLOPS on AMX" (`w4a8_quantizer.py:50`): M3 has no FP8 GEMM path — this manufactured 2× is exactly what makes W4A8 "pass" the SLA (`:97-101, :176`).
- "Nova 189.8 MB freed" (`vision_offloader.py:199, :222-228`): on unified memory, moving layers "GPU→CPU" frees nothing; the file's own header (`:25-28`) says so. Real mechanism would be SSD-backed swap at ~5-8 GB/s, not 100 GB/s.

### 1.10 🔴 Model identity is inconsistent across the repo (and probably wrong)
- KV/token "110,592 = 2 × 24 × **1152** × 2" (`README.md:180`, `kv_manager.py:37-38`): 1152 is the **SigLIP vision** hidden size. `calibration_results.json` says `hidden_size: 2048` — which matches SmolLM2-1.7B, i.e. the checkpoint is likely the **2B** SmolVLM, not "500M-param LM." SmolVLM-500M's LM is 32×960 with GQA (KV/tok = 81,920 B). GQA is ignored everywhere.
- `kv_manager.py:23-24` admits `hidden_size` was "calibrated from kv_cache_mb data" then "verified" against the same data — circular.
- Weight figures disagree three ways: `results.json` 63.9 MB / `controller.py:71-72` 250+200 MB / real 4-bit 2B ≈ 1+ GB.
- `cost_model.py:58` uses 2048 while `kv_manager.py`/`vllm_baseline.py` use 1152 → KV accounting differs 1.78× between files that feed the same pipeline.
- KV pool budget: 5694 MB (`kv_manager.py:52-54`, `controller.py:75`) vs 5742 MB (`sm_orchestrator.py:57`).
- `config/model_config.yaml` and `config/tp_simulation.yaml` describe LLaVA-7B/Qwen-VL on "M3 16GB" — a different, earlier study; no config file describes the SmolVLM actually used. `docs/DESIGN.md` likewise describes LLaVA-1.5-7B with success criteria pre-checked ✅.

### 1.11 🟠 Four contradictory decode baselines
0.03–6 ms (`results.json` resolution sweep, broken subtraction), 217.7 ms (`tbt_curve` — 60 bit-identical values), ~433 ms (batch_throughput), 1,111 ms (`sm_orchestrator.py:113`, `parallelism_engine.py:285`). The same file (`sm_orchestrator.py`) uses two of them. The "83.75 + 3.95·B" TBT model is labeled "measured" (`batching_engine.py:90-92`) but no data supports it.

### 1.12 🟠 W4A8 flagship result double-counts compression
`w4a8_quantizer.py:54` states the measured baseline was **already 4-bit weights**, then `analyze()` (`:174-198`) applies the FP16→W4 byte reduction to that baseline anyway. The genuinely new lever (A8) is worth ≤ ~1.5× under the module's own model. Also `:201-202`: the module's own numbers show FP16 decode needs only 4.6 GB/s of the 100 GB/s available — decode is overhead-bound, refuting the bandwidth-bound premise of the whole phase; the `bw_bound` flag (`:203`) is semantically inverted. "GAR" accuracy numbers (`:253-297`) cite "QuaRot, SpinQuant" for a technique matching no published method.

### 1.13 🟠 Fragmentation claim is tautological and doesn't reproduce
- Contiguous backend is *defined* to always allocate 2048 tokens (`kv_manager.py:82-141`); paged allocates exact-fit — so "62.8% → 5.3%" is the difference between two assumed policies, not a finding. Running the shipped sweep actually yields ~61.1% → 0.04%, so even the published numbers don't reproduce.
- The one measured value is 22.2% (`results.json`), acknowledged at README:82 yet replaced by 62.8% in the README:17 results table.
- Whether MLX's real allocator preallocates to max_seq_len (it grows in steps) was never established.

### 1.14 🟠 The "adaptive" controller degenerates to a constant
- With vision at 249.6 ms/crop and a 500 ms SLA, every strategy with ≥2 crops is infeasible by construction; the 96-strategy search returns (1 crop, keep=1.0, TP) or fallback — a two-outcome lookup (`controller.py:80, 86-89, 496-504, 582-601`).
- The ×2 parallelism dimension is dead: TP strictly dominates DP always (`:522-524, :594-601`).
- `image_resolution` is accepted and never read (`controller.py:139`) — resolution "adaptivity" cannot exist.
- `generate_report.py:249-252` admits Fig 2's strategy diversity was produced under a relaxed 3 s SLA ("the tight 500 ms SLA forces 1 crop everywhere") — disclosed only in a caption.
- `sm_decode` has zero effect on the controller's predicted decode cost (`controller.py:463-470, 529-533`), so Nova reallocation is modeled as pure upside — its benefit is an assumption, not a result. Note `sm_orchestrator.py:181-185` implements the *opposite-direction* SM rule from the README/controller formula.

### 1.15 🟠 Baseline measurement methodology (Phase 1) is broken
`baseline/run_experiments.py`:
- `:122-129` decode time = (two full generates subtracted)/40 — both include full vision+prefill; results show the `max(...,1.0)` clamp firing (0.03 ms "decode").
- `:135-137` p50/p90/p99 all set to the single mean — fabricated percentiles.
- `:146-183` "TBT curve" = whole-generate wall time / 20, replicated 20×; per-token latencies of 1.9 s in the data are physically impossible.
- `:186-216` "batch throughput" runs sequentially and includes prefill in tok/s.
- No warm-up, single trial per config (first run absorbs Metal JIT compile).
- Three different "baseline TTFT" values circulate: 8,489 / 8,536 / 8,617.81 ms.

## 2. Genuine logic/code bugs

### simulation/batching_engine.py
- 🔴 `:723-743` — inverted SM-contention: `sm_scale = sqrt(SM_MIN/sm_decode)` ≤ 1, floored at 0.85 → concurrent decode gets up to a **15% speed bonus** instead of a penalty. Directly inflates the 1.63× throughput headline (contention occurs mostly in the continuous engine).
- 🔴 `:596-598, :619-624` — `gpu_idle_ms += 0.0` (literal no-op) and the idle-accounting branch is dead code → continuous engine reports 100% GPU utilization **by construction**; static engine counts all vision+prefill as idle → apples-to-oranges.
- 🔴 `:869-879` — static engine double-counts padded decode into `gpu_active_ms` (~2.9× wall clock in skewed batches); active+idle ≠ duration.
- 🔴 `:578, :661-663` — the "FCFS" control arm sorts by `sjf_key` unconditionally at 2 of 3 scheduling points; the SJF-vs-FCFS comparison is SJF-everywhere vs SJF-mostly.
- 🟠 `:604-608` vs `:864` — TTFT off-by-one-tick only in the continuous engine (stamped at tick start, before the step's TBT elapses); understates continuous TTFT by 88–360 ms vs static.
- 🟠 `:90-111` — TBT(1)=87.7 ms > the 80 ms TBT SLA, so the SLA is unmeetable at any batch; header claims batch 70 keeps TBT ≤ 80 ms (actual: 360 ms).
- 🟠 `:576-598, :536-540` — if KV admission fails with an empty decode batch, no tick is rescheduled → requests silently never finish.
- 🟡 `:612` vs `:872` — avg/p99 TBT weighted per-tick (continuous) vs per-token (static). `:269-271` "max waiting time" actually records max TBT. `:426-432` `random_seed`/`self._rng` dead. `:690-704` vision cost constant regardless of the workload's varying `n_visual_tokens`. Single seed, no CIs, for all headline numbers.

### simulation/controller.py
- 🟠 `cost_model.py:194-203` (consumed at `controller.py:508-514`) — migration cost *decreases* with migration depth (inverted); true cost ≈ `(depth/24)·[T_prefill(N_full) − T_prefill(N_kept)]`, orders of magnitude larger → pruning looks nearly free.
- 🟡 `:582-601` — "Pareto selection" is lexicographic max over (crops, keep, −TTFT), not a Pareto frontier; would prefer (24 crops, keep .111, quality 2.66) over (21, 1.0, quality 21).

## 3. How to improve the study (prioritized)

1. **Measure the real system end-to-end.** Run actual `mlx-vlm` SmolVLM inference with genuinely varied image splitting; confirm `visual_tokens` changes (it didn't in results.json). Use `mx.eval(<output arrays>)` / `mx.synchronize()` — the current no-arg `mx.eval()` calls synchronize nothing. ≥10 runs per config, warm-up discarded, mean ± 95% CI.
2. **Resolve the 8,489 vs 2,498 ms gap empirically instead of inventing a vision stage.** Time the SigLIP forward in isolation (evaluate image-embedding tensors before the LM call). Retract "5,991 ms, Phase 1 measurement" until it's a real number.
3. **Disclose the 70.6% validation error; do honest held-out validation.** Leave-one-out CV or new N values not used in fitting; delete "held-out" from the README until true. Weight the fit by trial variance; constrain α ≥ 0; document the valid domain.
4. **Replace the crop-count quality proxy with a real benchmark.** Even 300–500 VQAv2/TextVQA/DocVQA samples per (crops, keep) setting. This is the single experiment that could make the "quality preserved" claim real — the whole design bets on 1 crop being acceptable.
5. **De-hardcode `generate_report.py`** — compute every table from pipeline outputs; fix the FINAL_REPORT/PHASE8_REPORT path bug; add a "Measured vs Modelled" column to every results table; add a one-line simulation disclaimer to the README results table.
6. **Fix the model identity.** Confirm which checkpoint ran (hidden 2048 ⇒ likely the 2B, not "500M"); derive KV/token as `2 × layers × n_kv_heads × head_dim × dtype_bytes` from config.json incl. GQA; centralize all constants in one module (currently: 2 hidden sizes, 2 pool budgets, 3 weight figures, 4 decode baselines, 3 KV/token values).
7. **Fix the comparison-corrupting bugs before re-running Phase 5:** inverted SM contention (decode speed bonus), idle-time accounting (100% util by construction), static double-count, FCFS-arm-runs-SJF, TTFT off-by-one — then re-run across ≥10 seeds with CIs.
8. **Remove fictitious hardware effects from headline numbers:** the ×0.75 single-chip "TP" discount, the FP8-on-M3 2×, the W4-on-already-W4 double count, the unified-memory "189.8 MB freed." Replace "38 SMs" with the M3's 10 GPU cores and rename Nova outputs as scheduling shares (FINAL_REPORT §2.3 already does; propagate to README). If TP matters, measure MLX distributed over two Macs, or report it strictly as a multi-GPU projection.
9. **Fair baseline:** the 512 px headline must compare against 9 crops (its own grid) → ~9×, not 24.4×; present the 24-crop case as worst-case separately. Standardize on one measured baseline TTFT.
10. **Make the live service real or honest:** wire actual model inference into the workers, fix `_n_decoding`, catch `MemoryError`, gate on `pr.wait()`'s result — or relabel the endpoint/telemetry as a simulation API and strip the fabricated OpenAI `usage` fields.
11. **External baselines + energy:** stock `mlx-vlm` generate, llama.cpp/Ollama on the same M3; `powermetrics` energy per request (the study is framed as edge inference).
12. **Real tests:** convert `test_phase4.py` to pytest functions that can fail (cost-model monotonicity, constants consistency across modules, report-path existence, α-domain checks, allocator invariants).

**Bottom line:** the salvageable core is (a) the 7-point prefill calibration and (b) the measured ~8.5 s end-to-end baseline. Reframed honestly as a *modeling/systems-design* study with the fixes above, this is credible work; as an experimental performance study, the headline claims are currently unsupported.
